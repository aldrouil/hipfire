## 1. Purpose

`jobsched` is a small dependency-aware job scheduler / state machine. Jobs are
added with dependencies on other jobs; a job becomes ready only when every job
it depends on has succeeded. Failures and cancellations propagate to
dependents, failed jobs can retry a bounded number of times, and dependency
cycles are rejected.

State names are the exact strings

## 3. Job admission

- `job_id` must be a non-empty string. A duplicate `job_id` raises
  `ValueError` with no state change.
- `priority` must be an `int` (bools are not valid priorities); `max_retries`
  must be an `int >= 0` (`True`/`False` are accepted as `1`/`0`, since only
  `priority` excludes bools). Otherwise `ValueError`, no state change.
- `deps` lists job ids the new job depends on. Every entry must name an
  already-added job, otherwise `ValueError` with no state change. Duplicate
  entries in `deps` are collapsed (they do not create duplicate edges).
  Depending on itself raises `ValueError` (cycle), no state change.
- The initial state of an admitted job is decided from its dependencies:
  no dependencies, or all dependencies `SUCCEEDED` -> `READY`; any dependency
  `FAILED` -> `FAILED`; else any dependency `CANCELLED` -> `CANCELLED`;
  otherwise -> `PENDING`. (`FAILED` takes precedence over `CANCELLED`.)
- Insertion order is recorded per job (a sequence number starting at 0 in
  admission order) and is used for tie-breaking in `ready_queue()`.

## 4. Dependencies after admission

- `add_dependency(job_id, dep_id)` adds one edge: both ids must exist,
  otherwise `ValueError`. It raises `ValueError` (no state change) when
  `job_id == dep_id`, when the edge already exists, when `job_id` is in any
  terminal state (`SUCCEEDED`, `FAILED`, `CANCELLED`), or when `job_id` is
  `RUNNING`.
- It raises `ValueError` (no state change) if the new edge would create a
  dependency cycle of any length, including an indirect one
  (e.g. A depends on B, B depends on C, then C depending on A is rejected).
- After a legal edge is added, the dependent job is re-evaluated with the rule
  in section 6 (so a `READY` job that gains an unfinished dependency goes back
  to `PENDING`; one that gains a `FAILED` dependency goes to `FAILED`).

## 5. Starting and completing

- `start(job_id)` moves `READY` -> `RUNNING` and increments that job's attempt
  counter by one. Calling it on a job in any other state (`PENDING`,
  `RUNNING`, terminal), or on an unknown id, raises `ValueError` with no state
  change. In particular a `PENDING` job is NEVER auto-promoted by `start`.
- `complete(job_id, ok=True)` requires the job to be `RUNNING`, otherwise
  `ValueError` with no state change.
  - `ok=True`: the job becomes `SUCCEEDED`; then dependents are re-evaluated
    (section 6), cascading transitively.
  - `ok=False`: if the job still has retries left (`retries_left > 0`,
    initialized to `max_retries`), decrement `retries_left` by one and
    re-evaluate the job itself with the rule in section 6 (normally back to
    `READY`, but `PENDING`/`FAILED`/`CANCELLED` if its dependencies no longer
    all succeed); otherwise the job becomes `FAILED` and dependents are
    re-evaluated, cascading transitively.
- `attempts(job_id)` returns how many times `start()` has succeeded for that
  job (0 for a never-started job).

## 6. Dependent re-evaluation (propagation)

Whenever a job enters `SUCCEEDED`, `FAILED`, or `CANCELLED` (including via
retry exhaustion, cancellation, or edge addition), every direct dependent is
recomputed, and any dependent that itself changes to a terminal state
propagates further, transitively:

- terminal dependents (`SUCCEEDED`, `FAILED`, `CANCELLED`) never change;
- a non-terminal dependent with any `FAILED` dependency becomes `FAILED`;
- else a non-terminal dependent with any `CANCELLED` dependency becomes
  `CANCELLED`;
- else a non-terminal dependent whose dependencies are all `SUCCEEDED`
  becomes `READY`;
- otherwise it becomes (or stays) `PENDING`.

A `RUNNING` job's dependencies are necessarily all `SUCCEEDED` already, and
`SUCCEEDED` never changes, so propagation never alters a `RUNNING` job.

## 7. Cancellation

- `cancel(job_id)` on a `PENDING`, `READY`, or `RUNNING` job moves it to
  `CANCELLED` and propagates to dependents with section 6 (a dependent with no
  `FAILED` dependency but a `CANCELLED` one becomes `CANCELLED`).
- `cancel()` on a terminal job or an unknown id raises `ValueError` with no
  state change.

## 8. Ready queue

- `ready_queue()` returns the ids of all jobs currently `READY`, ordered by
  `(priority ascending, insertion sequence ascending)`. Smaller `priority`
  integers mean more urgent (run first). Ties keep admission order (FIFO).
  It returns a fresh list; mutating it must not affect the scheduler.
